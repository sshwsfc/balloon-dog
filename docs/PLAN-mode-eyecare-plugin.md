# 模式切换 / 护眼设置 / 应用插件管控 —— 实现计划

本文对应家长端参考界面里的四个新页面：**切换模式**、**设置模式时段**、**选择应用**、
**插件管理**（微信/QQ 功能管控），以及顺带的 **护眼设置** 与 **应用审批** 入口。

---

## 0. 需求拆解

| 需求 | 落地形态 |
| --- | --- |
| 家长端首页参考该界面 | 九宫格分组 + 顶部「一键锁屏」通栏 + 顶部使用信息（今日时长/最多使用应用/最新动态） |

## 1. 三个必须先讲清楚的设计决定

### 1.1 「不设置则全天为学习模式」这条语义，我们照做但加硬提示

参考界面的原文是「不设置则全天为学习模式」。照做，因为那确实是家长勾选「按时间设置」
之后自己选的语义。但它是个**很容易把孩子手机一次锁死**的默认值（除了白名单应用，
什么都用不了），所以：

- 时段为空且「按时间设置」已开启时，家长端显示**红色警告条**说明「当前全天为学习模式」；
- 设备端日志明确记录「时段规划为空 → 全天学习模式」，便于排查「为什么一整天都不能用」。

### 1.2 学习模式的「拦截」用什么做：无障碍，不是系统 API

Android **没有**「只允许这些应用运行」的公开 API（除非做设备所有者 + Lock Task 白名单，
而 Lock Task 是把设备钉死在**单个**应用上，不适合「学习模式允许 5 个应用」）。

所以学习模式与插件管控都走**无障碍服务**：监听前台应用与界面内容，
命中限制就用 `GLOBAL_ACTION_BACK` 退回 + 显示一层说明遮罩。

这条路必须如实说明它的边界（会写进 `android/README.md`）：

- **按可见文本/资源 id 匹配**，应用改版改了文案就会失效 —— 所以插件匹配规则要写成
  「一组候选关键词」，而不是一条精确文本；
- **只能拦界面，拦不住内容**：WebView / 游戏画布里的东西看不见；
- **有几十到几百毫秒的延迟**，快速滑动可能闪过一帧；
- 关掉无障碍权限即失效 —— 但关权限本身会被看门狗与设备所有者限制挡住（见现有文档 §2.2）。

### 1.3 离线优先：设备端自己算，服务端只做下发与展示

学习模式的「当前该不该是学习模式」必须**断网也能算**，否则孩子拔网线就绕过了。
所以沿用作息时间表那套做法：

- 规则原样下发到设备端（`/agent/config`）；
- Android 用 `StudyModeEngine` 本地求值；
- 服务端 `mode.service.ts` 里有同一套求值逻辑，用于家长端展示「当前模式」；
- 两边用**交叉验证脚本**逐点比对（参照现有 `android:crosstest` 的做法），避免两套实现漂移。

## 2. 数据模型（Prisma）

```
DeviceMode        每台设备一行：manualMode（null=跟随时段）+ scheduleEnabled
StudyModeSlot     0–23 时 × 0–6（0=周日）的学习模式时段，唯一键 (deviceId, dayOfWeek, hour)
ModeApp           学习模式应用分组：group = 'study'（学习模式允许）| 'normal'（普通模式专用）
DeviceApp         设备上报的已安装应用清单（选择应用 / 插件管理的数据来源）
EyeCareConfig     护眼设置：连续用眼提醒、休息时长、夜间时段、亮度上限
AppPluginState    按 (deviceId, packageName, pluginKey) 的允许/禁止
DeviceEvent       设备事件流，供「最新动态」展示
```

星期沿用现有约定：**0=周日 … 6=周六**（与 JS `Date.getDay()`、`ScheduleRule.daysOfWeek` 一致）。

## 4. 插件目录（`APP_PLUGIN_CATALOG`）

服务端与设备端**各存一份**（设备端必须离线可用）。键名与含义必须一致，
所以两边用同一份「键 → 标签 → 匹配关键词」定义，并在文档中声明这是需要同步维护的。

覆盖范围（首批）：

- `com.tencent.mm`（微信）：支付、小程序、朋友圈、视频号、直播、游戏、扫一扫、
  摇一摇、附近的人、看一看、搜一搜、公众号、群聊、添加好友、转账、红包
- `com.tencent.mobileqq`（QQ）：支付、空间、游戏、直播、附近的人、看点、频道、群文件
- `com.tencent.mm`/`com.tencent.mobileqq` 通用：应用内支付
- 支付管理（跨应用）：游戏与应用内支付
- 应用商店类：`com.android.vending`、`com.huawei.appmarket` 等 —— 安装类插件
- 浏览器类：`com.android.browser` 等

每项含 `key / label / category / keywords[]`。匹配用关键词集合，降低改版失效风险。

## 5. Android 端

| 新增 | 职责 |
| --- | --- |
| `StudyModeEngine` | 本地求值「此刻是否学习模式」 |
| `StudyModeEnforcer` | 学习模式下的前台应用白名单拦截 |
| `PluginGuard` | 按插件规则匹配当前界面并拦截 |
| `EyeCareController` | 连续用眼计时 → 强制休息；夜间时段；亮度上限 |
| `AppInventory` | 收集已安装应用并上报 |
| `EventReporter` | 设备事件上报（解锁/锁定/亮屏/装应用/拦截） |

不新开服务（多开一个无障碍服务只会让用户多授权一次，且更容易被系统回收）。

## 8. 明确不做 / 做不完整的（先声明）

- **护眼的「距离/姿势提醒」**：需要前置摄像头持续取帧并做人脸/距离推断，
  隐私代价与误报率都很高。首批**不做**，也不放一个假开关。
- **「学习模式专用桌面」**：参考界面说「手机显示特定桌面」。换桌面需要设备所有者
  或用户手动切换，首批**不做**，只限制应用使用。
- **应用审批的强制拦截**：Android 没有「安装前弹给家长审批」的公开 API。
  首批做到「设备所有者 + `DISALLOW_INSTALL_APPS` 关上安装 + 无障碍上报审批请求」，
  家长批准后**临时放开**一段时间。这一点必须在界面上写清楚，不能假装是系统级审批。
- **插件管控拦不住内容**：见 §1.2，WebView / 游戏画布内的内容看不见。

**关于主套件的回归数字**：本轮功能没有改动拍照、应急解锁这两条链路，
但多次运行里它们偶发失败 —— 拍照是模拟器的 `ERROR_CAMERA_DEVICE(4)`（同一版本上一轮
83/83 时是过的），应急解锁是「点锁定页上的按钮」这类 UI 时序抖动。
两种都不是本轮引入的问题，但**如实记在这里**，不修饰。

设备端那条是最有说服力的：**在真实模拟器上**——
普通模式能打开「时钟」→ 手动学习模式把它拦回（且日志有拦截记录）→
按时段的学习模式同样拦回 → 加入白名单后又能打开 → 切回普通模式恢复。

### 9.3 计划外发现并修掉的问题

1. **Android 11+ 的软件包可见性会让学习模式静默失效。**
   不加 `QUERY_ALL_PACKAGES` 时，`queryIntentActivities` 只返回极少数包
   （实测只拿到 1 个），于是「选择应用」列表几乎是空的，
   更要命的是 `AppInventory.isLaunchable()` 一律为 false ——
   **拦截判据直接不成立，家长设了完全不起作用**。已在清单里声明该权限并注明它的敏感性。

2. **插件目录不需要在设备端再存一份。**
   计划里写的是「两端各存一份、必须同步维护」。实现时发现设备端只用得到
   **规则**（包名 + 键 + 是否允许 + 匹配关键词），而这些东西随配置一起下发并落盘，
   断网照样生效。所以设备端**没有**目录副本 —— 也就没有「两边漂移」这个风险源。
   这是比计划更好的做法，已按此实现。

3. **`PUT /api/eye-care` 曾经先写库再校验。**
   矛盾的夜间配置会被拒绝并返回 400，但**已经写进数据库了** ——
   「报错了但其实生效了」是最难查的一类问题。已改为先算最终值、校验通过才落库，
   并在 `server:e2e:mode` 里加了断言钉住它。

4. **`z.coerce.boolean()` 会把 `"false"` 变成 `true`。**
   JS 的 `Boolean("false") === true`，所以 `?includeSystem=false` 的含义正好相反。
   已换成显式解析，并加了回归断言。

5. **护眼强制休息不能被临时解锁绕过。** `LockState` 里护眼判定排在最前，
   家长临时解锁、答题奖励都不能取消「让眼睛休息」——
   一个能被「再答一道题」绕过的护眼提醒没有意义。

### 9.4 与计划不同的一处语义

计划 §1.1 说「不设置则全天为学习模式」照做。实现时保留了这条语义，
但**同时**在家长端给出 `allDayStudyWarning` 红字警告，并在设备端日志里明确记录
「时段规划为空 → 全天学习模式」，避免出现「为什么一整天都不能用」这种无从下手的反馈。

### 9.5 诚实的边界（说清楚比假装做到重要）

- **学习模式与插件管控走无障碍，不是系统 API。** Android 没有「只允许这些应用运行」的
  公开接口。因此：按可见文本匹配（应用改版会漏拦）、看不见 WebView / 游戏画布里的内容、
  有几百毫秒延迟、关掉无障碍权限即失效（但关权限本身会被看门狗挡住）。
- **插件关键词匹配没有在模拟器上端到端验证** —— 模拟器里没有装微信/QQ，
  复现不出「朋友圈被打开」。所以这部分抽成纯函数 `GuardRules`，由 `GuardCheck`
  用合成界面文本逐条覆盖；设备端只验证「规则能下发并落盘」。
  与其写一条永远跑不到的端到端断言（等于没测），不如这样分工。
- **护眼的「距离/姿势提醒」没做**，也没放假开关：需要前置摄像头持续取帧，
  隐私代价与误报率都太高。
- **「学习模式专用桌面」没做**：换桌面需要设备所有者或用户手动切换。
- **应用审批不是系统级审批**：Android 没有「安装前弹给家长审批」的公开 API。
  界面上如实写明它实际是「设备所有者禁用安装 + 无障碍上报审批请求 + 临时放开」。
- **「最多使用应用」是近似值**：后端没有按应用统计使用时长的接口。
  首页那块用最近屏幕洞察的活动片段出现次数排序，并明确标注「不是精确的使用时长排行」。
