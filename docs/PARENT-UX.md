# 家长端功能地图与交互逻辑

> 这份文档回答三个问题：
> 1. 家长端一共有哪些功能，分别在哪一页？
> 2. **为什么这样布局**？
> 3. 哪些功能需要先开开关，开关在哪？
>
> 姊妹文档 [`docs/FEATURE-STATUS.md`](FEATURE-STATUS.md) 回答的是另一个轴 ——
> 「家长在网页上点了之后，孩子手机上到底会不会真的发生什么」。
> 本文只管**家长端自己的信息架构与交互**，不重复那份文档的三端对照表。
>
> 涉及页面代码时只给路径和行号，不贴实现 —— 行号会漂，以符号名为准。

---

## 0. 一句话模型

家长端里只有两种东西：

- **看板**：孩子现在什么状态（首页、位置、洞察、我的）。
- **动作**：改一个设置，或者下发一条指令。

后面所有布局决定都来自这一条：**看板要一眼看完，动作要一步到达。**

「一步到达」是本轮改动的主线。原来家长端最大的问题是**动作被拆成了两跳**：
先回首页找到功能开关打开，再回到功能页使用。跳一次是小事，跳一次之后还要
「回想刚才在哪一格」，就是可用性问题了。

## 1. 六条布局原则

### 原则 1：一级导航只放「每天都会看一眼」的东西

一级导航（底部栏 / 宽屏侧栏）是屏幕上最贵的位置，只放四个：

| 入口 | 路由 | 为什么是它 |
| --- | --- | --- |
| 首页 | `/` | 唯一的「总览 + 总闸」入口，其余一切都能从这进去 |
| 位置 | `/location` | 家长最高频的焦虑点，独立成页是因为地图本身要占满屏 |
| 洞察 | `/insights` | 三类报告（游戏时长 / 动画集数 / 不适龄内容）的入口，**每天会看**；调开关去标题栏「配置」→ `/insights/config` |
| 我的 | `/profile` | 设备列表、**会员中心（`/membership`）**、**邀请返现（`/referral`）**、媒体库、语言、新手引导复位 —— 低频但对的东西 |

**为什么是这四件**：判断标准是「家长会不会主动、反复地打开它」。
「定时锁屏」「应用限制」这类是**配置**，配一次管很久，不配一级入口；
把它们塞进一级导航会让导航变成设置项的垃圾桶。

**「洞察」是这一轮才提上来的。** 它原本只是首页「最近活跃应用」卡片右上角
一个 11px 的灰字链接 `查看洞察`（[`src/pages/HomePage.tsx`](../src/pages/HomePage.tsx)）。
入口太弱直接导致这一页事实上不可达 —— 家长的反馈原话是
「AI 洞察的入口按钮太不明显了」。现在做了两件事：把它加进一级导航，
同时把首页那个文字链换成**实心绿按钮**（带图标，`h-7` 而不是 11px 文字）。
首页那张摘要卡**保留**：它回答「今天怎么样」，洞察页回答「为什么」，
两者不是替代关系。

### 原则 2：首页是「总闸 + 总览」，不是唯一入口

首页同时承担两件容易混淆的事，必须分开看：

- **总览**：设备状态、今日时长、最近动态、最近媒体 —— 只读。
- **总闸**：十项功能开关 —— 写，且影响别的页面能不能用。

**为什么要保留首页那十项开关**：它是一个全局视角。家长想知道
「我到底给孩子开了哪些能力」，只有在同一屏里横着比才看得出来；
把开关全部下沉到各自的功能页之后，这个视角就没了。

**为什么不能只有首页那一份**：因为它是**两跳**的根源。
所以定下的规则是「**总闸留在首页，同时每个功能页都能就地开启**」——
同一份状态，两个入口，谁都不替代谁。

### 原则 3：需要开关的功能，开关必须在功能页就地可用

这是本轮改动的主体。后端有一层「功能门禁」：`requireFeatureEnabled()`
（[`server/src/features/devices/devices.service.ts`](../server/src/features/devices/devices.service.ts)）
在开关没打开时直接抛
`BadRequestError('请先开启「${label}」功能')`。

原来的体验是：家长在**远程协助**页点「取屏」→ 弹一句
「请先开启「同屏监控」功能」→ 家长得回首页、在下方的十项开关里找「屏幕洞察」
→ 打开 → 再走回远程协助页。**这就是用户抱怨的「跳来跳去」。**

现在的做法是就地解决，用三个形态覆盖三种页面结构：

| 形态 | 组件 | 用在哪 | 长什么样 |
| --- | --- | --- | --- |
| 整页门禁 | `<FeatureGate variant="page">` | 整页功能都依赖同一个开关 | 开关没开时**整页替换**成说明 + 「开启」按钮 |
| 行内门禁 | `<FeatureGate variant="inline">` | 只有某一小块需要开关 | 只替换那一块，其余内容照常可用 |
| 缺开关提示 | `FeatureEnableCard` | 页面主体还能看，只有某个动作需要开关 | 页面顶部一张 amber 卡片 |

组件在 [`src/components/FeatureGate.tsx`](../src/components/FeatureGate.tsx)，
导出 `FeatureGate` / `FeatureEnableCard`；开关状态与开启动作在
[`src/hooks/useFeatureToggle.ts`](../src/hooks/useFeatureToggle.ts) 的
`useFeatureToggle(feature)`（单独成文件是为了让组件文件只导出组件，保住 HMR）。
`FeatureGate` 内部就用它，所以页面里「主体用卡片门禁、页头按钮只要禁用」时
两处共享同一份状态，不会各发一次请求。

**首页九宫格也补了就地开启**：像「远程拍照」这种格子，点下去等于直接下发指令，
但开关在页面下方 —— 现在会先弹一个「远程拍照还没开启 / 开启后才能下发这条指令，
现在开启？」的小框，点一下开完就走，不用滚下去找开关。

### 原则 4：提示语只回答「下一步做什么」

原来的文案普遍是**解释**而不是**指令**：一句话里塞了「这是什么 + 为什么这样
+ 例外情况 + 注意事项」。家长要的是「我现在该点哪」。

改写后的三条规矩：

1. **先给动作，再给理由**，理由压到一句。
2. **能省的字都省**：「请」「您」「即可」「以便」「该功能」全去掉；
   短提示不加句号。
3. **事实不删，只压缩**：隐私（截图会交给 AI）、权限（无障碍服务）、
   限制（必须孩子端在线）这类说明必须留下，因为它们决定家长要不要用这个功能。

用词统一为「**孩子端**」（不再混用「孩子设备端 / 孩子的设备 / 孩子的手机」）。

### 原则 5：不确定就不要拦

`FeatureGate` 和 `RequireDevice` 共享同一条取舍：
**只在确知功能没开时才拦人。**

| 情况 | 处理 | 为什么 |
| --- | --- | --- |
| 还在读取开关状态 | 显示转圈占位 | 不知道就不下结论 |
| 读取失败（网络问题） | **放行** | 把网络故障说成「功能没开」，家长会白找一圈 |
| 后端没返回该标识 / `enabled` 不是布尔 | **放行** | 前端多列一个标识时不该把功能锁死 |
| 明确读到 `enabled === false` | 拦，并给出就地开启 | 这才是真正需要提示的情况 |

真正的把关始终在后端。前端这层只负责**别让家长白跑**。

### 原则 6：页面标题栏固定在顶部

`.page-header`（20 个页面都有，含首页的「设备监控」）在 CSS 里是
`position: sticky; top: 0; z-index: 30`
（[`src/index.css`](../src/index.css)）。家长端的页面普遍偏长
（首页四个九宫格组、洞察页的时间线），滚到中段时**当前在哪个页面、
能不能刷新或返回**必须一直看得见，否则只能滚回顶部确认。

两条实现取舍：

- **用 `sticky` 而不是 `fixed`**：标题栏靠「负 margin 抵消 `.page-shell` 留白
  + 自己补回等量留白」实现通栏（见 `index.css` 里的注释）。一旦脱出文档流
  就得自己重算一遍宽度，等于把那套算法抄两遍，删一处另一处就错位。
- **`z-index: 30`**：低于底部导航 / 左侧栏（`z-50`）和浮层提示（`z-40`），
  高于普通卡片，所以卡片不会盖住标题栏。`≥1024px` 时主内容已让出 224px
  侧栏宽度，标题栏跟着从 `x=224` 起算，不需要额外补偿。

## 2. 一级导航

- 组件：[`src/components/BottomNav.tsx`](../src/components/BottomNav.tsx)，
  一份 `navItems` 渲染两种形态 —— 窄屏底部固定栏、`≥1024px` 左侧竖排侧栏。
  刻意用 CSS 而不是 `useMediaQuery`：纯 CSR 应用里 JS 方案首帧必然错位。
- 不显示导航的路径：`/login`、`/quiz-unlock`、`/media`、`/onboarding`
  （见 `AppShell` 的 `hideNavPaths`）—— 这四条都是「沉浸式流程」，
  中途给导航会诱导用户跳出。
- 有导航时根节点加 `.has-nav`，`FeatureTip` 靠它决定浮层位置。

## 3. 首页从上到下

[`src/pages/HomePage.tsx`](../src/pages/HomePage.tsx) 是全局最长的一页，
顺序是**按「家长打开这一页想知道什么」排的**，不是按功能重要性：

| # | 区块 | 内容 | 为什么在这个位置 |
| --- | --- | --- | --- |
| 1 | 设备概览 | 设备名、在线状态、电量等 | 一切判断的前提：孩子端在不在线 |
| 2 | 一键锁屏（通栏） | 锁定/解锁 + 可编辑的快捷操作栏 | 最紧急的动作放最上面，通栏是为了在手机上够得着 |
| 3 | 今日概览 | 今日使用时长与上限、最近活跃应用、最新动态 | 「今天怎么样」的三连问，一屏答完 |
| 4 | 用量上限 | 每日使用时长 / 游戏局数 / 动画集数 | 紧接「今天用了多少」给出「用到多少就锁」，看与改在同一个位置 |
| 5 | 九宫格功能分组 | 四组共 24 个格子（见下） | 主功能区。分组是按**家长的心智分类**，不是按代码模块 |
| 6 | 功能开关 | 十项能力总闸 | 写在总览之后：先看现状，再决定开什么 |
| 7 | 环境监听 | 单独的卡片 | 有常驻通知、涉及隐私，单独一张卡更容易讲清楚 |
| 8 | 最近指令 | 指令队列与执行状态 | 排查「我点了怎么没反应」的地方 |
| 9 | 最近媒体 | 照片 / 截图缩略图 | 内容型产出，放最后 |

九宫格的四组（`TILE_GROUPS`）：

| 组 | 格子 |
| --- | --- |
| 设备和应用限制 | 模式切换、护眼设置、屏幕时间、应用限制、应用审核、网址拦截、定时锁屏、一键锁屏、临时可用 |
| 应用管控 | 微信管控、QQ 管控、功能管控、应用审批 |
| 远程监控 | 屏幕洞察、远程拍照、连续录像、远程录音、截图、定位、远程协助、通话短信 |
| 孩子管理 | 孩子设置、家庭成员*、隐藏图标 |

\* 「家庭成员」后端没有多家长模型，点击只给一句诚实的「当前版本尚未实现」，
不弹假的成功提示。

**九宫格与功能开关为什么是两块、不能合并**：
九宫格是「**执行动作**」，功能开关是「**启用/停用能力**」，
是同一功能的两个维度。合并过一次，结果是一次点击发两次请求。

### 用量上限：三条限制放在一起

[`src/components/UsageLimits.tsx`](../src/components/UsageLimits.tsx) —— 一张卡里放三条
**同构**的限制：每日使用时长（分钟）、游戏局数（局）、动画集数（集）。

它们为什么必须在一起：三条的语义完全一样，都是「**达到条件就自动下发锁屏指令**」，
差别只在计量单位。以前时长在首页、局数与集数散在洞察页，家长要配一套「今天最多玩多久」
得跑两个页面，而且两处的心智模型看起来还不一样。合并后每一行都是
「图标 + 名称 + 说明 + 设置」，已有的上限在下面按应用列出，带启用开关 + 编辑 + 删除。

**局数与集数依赖「屏幕洞察」**：这两个数字要靠截屏 + AI 分析才能数出来。没开洞察时
这两组会收成一条琥珀提示 + 一个「开启屏幕洞察」按钮（就地开，不用跳去首页）；
时长上限不受影响，它只依赖孩子端上报的使用时长，仍然随时可配。

**这一页只是「改」，洞察页是「看」**：`/insights` 底部那张只读的用量上限卡片
（带「去首页设置」）是同一份数据的另一个视图，两边不会各自长出一套配置。

### 洞察页先给结论、后给配置，配置另有专页

`/insights` 的排布顺序是 **异常提醒 → 洞察时间线 → 用量上限（只读） → （无配置）**：
家长打开这一页是想知道「孩子今天都干了什么、有没有风险」，
配置是低频动作，所以原本占半屏的「截屏与 AI 设置」整块搬到了
[`/insights/config`](../src/pages/InsightsConfigPage.tsx)，入口是**标题栏上的「配置」按钮**。

拆页的直接原因：那一页曾经把「三类报告 + 一条时间线 + 十几个开关 + 四个数字输入框」
堆在同一屏，家长滚两屏都到不了底部，而真正每天要看的结论反而被开关压住了。
开关本身没变（截屏总开关、四个数值项、AI 分析、答题出题、五个异常提醒类型），
只是换了一个「点进来就是来调它的」的落点。

### 会员中心：三档权益与「锁住的功能怎么提示」

家长账号分三档：**普通 / 会员 / 超级会员**（[`/membership`](../src/pages/MembershipPage.tsx)）。
会员 = 答题解锁 + 远程监控全部功能 + 绑定多台手机；超级会员 = 会员全部权益 + AI 洞察。
普通账号可以绑 **1 台**设备，多绑要会员。

- **入口**：「我的」页第一张卡片（`Crown` + 档位徽标），不在底部导航里 ——
  充值是一次性动作，放在一级导航会天天占着位置蹭点击。
  会员到期前或功能被锁时的「去开通」按钮都会跳到这一页。
- **「会员中心」不进 `RequireDevice`**：绑设备本身是会员权益，
  如果充值页也要求先绑设备，新账号就会卡在「想绑第二台 → 要会员 → 要会员先绑设备」的死循环里。
- **被锁的功能怎么表现**：能整页锁的（`/media`、`/call-sms`、`/remote-help`、
  答题解锁、AI 洞察与它的配置页）用 [`MemberOnlyPage`](../src/components/MemberOnlyPage.tsx)
  或 [`MembershipGate`](../src/components/MembershipGate.tsx) 直接换成升级引导卡片；
  首页那些总闸开关**锁住时不渲染开关**，只渲染「去开通」——
  禁用的开关点下去毫无反馈，家长会以为页面卡了。
  绑定第二台设备的按钮同理，换成带说明的升级引导。
- **判断放在服务端**：前端这些提示只是「别让家长白填一遍表单再被 403 弹回来」，
  真正的把关是 `server/src/features/membership/membership.guard.ts` 里的 `requireEntitlement`，
  拦截后返回 `403 MEMBERSHIP_REQUIRED`（detail 带 `requiredTier` / `entitlement` / `currentTier`）。
- **付款页是模拟的**：环境变量 `MEMBERSHIP_MOCK_PAY=true`（默认）时点「确认支付」直接开通，
  页面顶部有琥珀色说明；接真实渠道时把它关掉，`payOrder` 会返回 503。
- **金额由服务端算并快照进订单**：前端传的价格一律忽略（否则改请求体就能一分钱开会员），
  订单详情里能看到下单那一刻命中的每一条规则。
- **受邀注册的账号价格更高，而且页面把原因说清楚**：邀请人拿到的返现是平台出的成本，
  所以被邀请的家长在常规定价之上再加一档（后台 `/admin/membership` 的「受邀用户定价」页维护：
  上浮比例 / 加收固定金额 / 一口价）。页面在档位卡片上方渲染一条说明条，三种状态分开说：
  ①生效了 → 橙色条「受邀用户定价已生效（本单多付 ￥X）」+ 命中的规则名；
  ②有资格但没生效（首单限定已过、或规则配得比常规价还低）→ 灰色说明条，
  **把服务端给的 `reason` 原样显示**（例如「常规定价已经不低于这条受邀定价规则，规则不生效」）；
  ③不是受邀账号 → 不显示这条（没有资格时不提示，否则等于平白告诉家长「这里本来可以更贵」）。
  加价额在套餐卡里单独一行**灰色**标签（`规则名 +￥X`），刻意不混进那排琥珀色优惠标签 ——
  它是要家长多付的，画成优惠就是欺骗。
  这些文案一个字都不在前端判断，全部读服务端的 `referral.applied` / `surchargeCents` / `reason`
  —— 规则后台一改，前端不用跟着发版。

### 邀请返现：把「分享」做成两条真能用的路径

[`/referral`](../src/pages/ReferralPage.tsx) 是「我的」页的第二张卡片（橙色 `Gift`），
放在会员卡正下方 —— 「会员要花钱」和「邀请能赚钱」是同一组心智。

- **分享按钮不假装能拉起微信**：纯网页在没有微信 JS-SDK 授权（需要公众号 appId +
  签名接口）时**无法**调起分享面板。所以「分享微信 / 分享朋友圈」的真实行为是
  **复制邀请文案**并 toast 提示「去微信里粘贴」，另外给「当面扫码」展开二维码。
  与其做一个点了没反应的按钮，不如给两条真的能用的路径。
- **分享链接的 origin 由前端拼**（`window.location.origin + linkPath`）：
  后端 `publicBaseUrl()` 是给服务端发通知用的，让它猜前端域名迟早会猜错。
- **邀请码用大字号等宽显示**（`font-mono tracking-[0.2em]`），因为它是拿来念给朋友听、
  或者手抄的；字符集刻意去掉了 `0/O/1/I/L`。
- **提现条件做成清单**（截图里没有，刻意加的）：四条门槛逐条显示「当前值 / 还差什么」，
  而不是让家长点一次提现、被 400 弹回来一次。未实名时按钮直接变成「去完成实名认证」。
- **实名表单明说「服务端只保存哈希值，不保留明文」**：家长要填身份证号，
  不解释清楚就会被当成又一个收集个人信息的页面。
- **数字口径写进页面**：收益卡把「总收益」拆成「待发放 / 已提现 / 待提现」，
  因为规则是**次月 10-15 日发放**，不拆开的话家长会以为当月的钱丢了。
- **奖励说明逐条渲染**（`config.noticeLines`）：换行交给后端切成数组，
  让前端 split 会在不同平台的换行符上飘。

### 紧贴「一键锁屏」下面的快捷操作栏

[`src/components/QuickActionBar.tsx`](../src/components/QuickActionBar.tsx) 那一行
（`快捷操作` + 右上角`编辑`）是**全页唯一可以改布局的地方**，默认放「临时可用 / 答题解锁」
—— 也就是它替换掉的那两个写死的按钮。

它解决的是一个具体矛盾：家长每天真正反复点的就那么两三个，但**「哪两三个」因人而异**。
写死两个按钮，总有一半人每天要往下滚到九宫格里去找自己想要的那个。
所以改成家长自己排，最多 8 个（一行四个、两行封顶，再多首屏就被这栏吃光了）。

可选项**直接从 `TILE_GROUPS` 派生**，不另立一套 id —— 这样它和九宫格共用同一个
`handleTileAction`，不会再出现「九宫格里能点、快捷栏里点了没反应」的错位。
只有两处调整：滤掉 `unsupported` 的格子（快捷操作是天天点的东西，
放一个点下去只说「当前版本尚未实现」的按钮没意义），以及补上「答题解锁」
（它原来只是「立即锁定」下面写死的第二个按钮，没有九宫格入口）。

编辑弹窗里有三件事：**添加**（下方按九宫格分组列出还没加的）、
**删除**（每行右侧 ✕）、**挪动位置**（每行 ↑ ↓，到头/到尾时对应箭头置灰）。
改动**立即生效、没有「保存」按钮** —— 这是上面「就地开关」那一类的路子，
不是「表单配置」。

## 5. 六种交互模式

改这一块之前先认出属于哪一种，六者的正确做法完全不同。

| 模式 | 特征 | 正确做法 | 例子 |
| --- | --- | --- | --- |
| **就地开关** | 一个布尔能力 | 就地 `FeatureGate` / `FeatureEnableCard`，开完立即生效，不需要「保存」 | 远程协助、通话短信、截图 |
| **指令下发** | 让设备立刻做一件事 | 乐观提示 + 队列语义：离线时如实说「指令会排队」，不要假装成功 | 锁屏、拍照、录像、定位刷新 |
| **表单配置** | 一组需要保存的设置 | 显式「保存」按钮 + 未保存提示；不自动提交 | 定时锁屏规则、模式时段、护眼参数 |
| **只读列表** | 分页展示历史数据 | 分页、空态、加载态三件套；失败要说清是「读不到」还是「没有」 | 通话短信、应用审批、媒体库 |
| **手动刷新** | 重读当前页数据 | **图标必须转圈并在转的时候禁用**，否则家长会以为没反应而连点 | 各页标题栏右上角 |
| **用户自定义** | 家长自己决定首页放哪几个按钮 | 改动立即生效；只存本机；存储里只放 id，图标与名称留在目录里 | 首页快捷操作栏 |

**「指令下发」的模式必须说清离线语义**，这不是文案洁癖：
后端把指令入 `DeviceCommand` 队列，设备离线时会一直 `pending`，
家长若以为「点了就是立刻发生」，会得出「这功能坏了」的错误结论。

**「手动刷新」为什么单独拧出一个组件**：各页面的刷新都是 **`silent`** 的
（不翻整页 `loading`，免得数据一变就闪骨架屏），代价是点了毫无视觉反馈。
统一用 [`src/components/HeaderRefreshButton.tsx`](../src/components/HeaderRefreshButton.tsx)：
转圈**至少 600ms**（否则本机接口 30ms 就回来了，动画一闪而过等于没做），
转的时候按钮 `disabled` 且 `aria-busy`，并用 ref 而不是 state 挡重复点击
——state 在同一帧里还是旧值，挡不住连点。
例外只有 [`CallSmsPage`](../src/pages/CallSmsPage.tsx)：它的刷新转圈跟页面里
「立即让设备重新读取」按钮**共用同一个 `syncing` 状态**，所以留在原地，
没有为了统一而把那个状态提上来。

**「用户自定义」为什么只存本机、而且只存 id**：快捷操作是「我这个家长的操作习惯」，
不是孩子账号的配置，没必要也不应该同步到服务端，所以放 localStorage
（键 `balloon_dog_quick_actions_v1`）。存储里**只放 id 数组**，
图标和名称留在 `TILE_GROUPS` 目录里 —— 将来改个图标或叫法，用户存下的顺序不会跟着失效；
反过来真删掉某个功能时，读出来会被过滤掉，不会渲染成一个空白按钮。
两个容易写错的地方：**用户在存储里写的东西一律不可信**（非字符串、重复项、
不认识的 id、甚至整段 JSON 坏掉，都要能兜住），以及**「全删光」存下 `[]`
是合法状态**，不能被当成「没存过」而弹回默认 —— 那样就永远删不完了。

## 7. 已知的粗糙处

如实列在这里，避免下一个人重新发现一遍：

1. **`/mode`、`/eye-care`、`/app-plugins` 没有就地开启。**
   这三个功能的开关（`modeSwitch` / `eyeCare` / `appPlugin`）
   在后端**没有接口级门禁**，页面本身能正常用，所以不存在「被拦下再跳回首页」
   的问题。但家长如果是从首页关掉开关再进来的，页面上看不出「这个能力是关着的」。
2. **首页九宫格与「功能开关」的对应关系不是一一对应。**
   九宫格有 24 格，开关只有 10 项：多数格子是**动作**，少数是**页面的入口**，
   真正的开关只有那 10 项。这是设计而不是疏漏，但它确实要求家长理解
   「动作」和「能力」的区别。
3. **`/location`、`/insights` 的「无设备」态依赖 `RequireDevice`。**
   该守卫在本轮修过一个首帧误判（设备列表还没加载完就把家长弹进新手引导），
   见 [`src/contexts/DeviceContext.tsx`](../src/contexts/DeviceContext.tsx) 里
   `loading` 初值与 `reload` 的注释 —— 动那个文件前先读注释。
4. **管理后台不在本文范围内。** 它按设计只做中文，
   信息架构也完全不同（[`src/admin/`](../src/admin/)）。
