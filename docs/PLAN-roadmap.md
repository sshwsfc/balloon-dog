# 下一阶段功能规划（设备健康可见性 · 家长端 · 孩子端）

> 这是**规划**，不是契约。定下来要做的项，再按 [`PLAN-agent-gaps.md`](PLAN-agent-gaps.md)
> 的写法单独出契约（字段名 / 三端改动 / 验收标准），避免三端各自发明字段。
> 现状以 [`FEATURE-STATUS.md`](FEATURE-STATUS.md) 为准（含 §3A 的验证等级与 §4.3 的诚实边界）。

## 0. 先定判断标准：现在哪一环是「看不见的」

孩子端 20+ 项能力都是真执行（§1 总览）。但它们**全都压在两三个开关上**：

| 被关掉的东西 | 连带失效 |
| --- | --- |
| **无障碍看门狗** | 学习模式、微信/QQ 管控、应用限制、免授权截图、远程协助、锁定页拉回 —— 全失效 |
| **设备所有者** | 防卸载、防强停、禁装、`OwnerHardening` 的 20 条限制 —— 全失效，孩子可直接卸载 |
| **定位权限** | 安全区彻底失灵（设备端本地围栏也拿不到坐标） |
| **电池优化白名单** | 息屏后被 Doze 冻结，心跳与指令延迟，表现为「指令点了没反应」 |
| **VPN 授权 / 永久 VPN** | 网址拦截停（快捷开关一划就能断） |
| **使用情况访问** | 逐应用限时与今日时长统计不生效 |

孩子端**自己知道**这些：`LongevityGuard.problems(Context, AgentStore)` 每 5 分钟算一次，
`LongevityGuard.describe(...)` 能把整段状态铺开。但**家长端看不到**：

- `ChildDevice` 只有 `status / battery / network / agentVersion / lastActiveAt / effectiveLocked / lockReason`；
- 缺口只以动态流里一条 `tamper` 事件的形式偶发出现（`LongevityGuard.report()` 是集合差分，
  新增/修复才发一条），家长不翻时间线就永远不知道；
- **没有任何接口承载「当前有哪些开关是开的」**，也没有「重新检测」指令。

一句话结论：**把「设备端自己知道的事」变成「家长端一眼看得见 + 一点就能修」。**
这是第一优先级，也正是「家长端要显示孩子端的权限开启情况」这件事。

## 1. P0-A 设备健康与权限可见性

### 1.1 孩子端上报一份健康快照

> **状态：✅ 已完成** —— `POST /api/agent/health`（覆盖式快照）+ `DeviceHealth` 表 + `GET /api/device/health`；

| 分组 | 字段 | 设备端来源（已存在） |

`problems` 直接存设备端下发的那句中文，家长端**不再翻译一遍** —— 否则迟早出现
「设备说无障碍被关、家长端说悬浮窗被关」这种两边描述不一致。

**心跳**只带一个摘要（`openGaps` + `level`），用于首页角标；完整快照走专用接口。

### 1.4 一键修复：把「报错」变成「修好」

> `server/src/features/devices/devices.fix-steps.ts` 按设备 `model` 认品牌（小米/华为/OPPO/vivo/三星，

- **能自动修**：无障碍重开、运行时权限（设备所有者下 `PermissionGranter.grantAsDeviceOwner()`

### 1.5 掉线与「失联」分级

> **状态：✅ 已完成** —— `liveness` 五档（2 分钟 / 30 分钟 / 24 小时）+ `agent_offline` 动态（6 小时去重）
> + 首页红条与健康分合并展示。

现状：只有 `status: online|offline`，而且家长点了指令才知道离线（`devices.service.ts:195`）。

- 按 `lastActiveAt` 分级：< 2 分钟 在线 / 2–30 分钟 心跳延迟 / > 30 分钟 失联 / > 24 小时 严重

### 1.6 时钟可信（`serverTime` 曾经是死字段）

- 服务端已经在心跳/配置里回了权威时间：`agent.controller.ts:190,237`、`devices.service.ts:747`、
  `mode.service.ts:143`；**Android 侧零引用**（`grep serverTime` 只有 `AgentApi` 的解析）
- 设备端所有时间判定都走 `System.currentTimeMillis()`（墙钟）：
  `LockWatchdogService:437` 的 `LockEnforcer.buildInputs(store, System.currentTimeMillis())` 等
- 设备所有者时 `DISALLOW_CONFIG_DATE_TIME` + `DISALLOW_CONFIG_TIMEZONE` 已经挡住系统设置改时间；
  **非设备所有者时没有任何兜底** —— 孩子把时间调回昨天就能绕过定时锁屏 / 屏幕时间 / 护眼计时
- 修法：以 `SystemClock.elapsedRealtime()`（单调，改墙钟不动）为基准，每次心跳用 `serverTime`
  锚定，得到墙钟偏移；偏移跳变超阈值 → 记 `tamper` 事件 + 上报 `clockSkewSeconds`；
  所有判定统一走 `TrustedClock.now()`
- 验收：`PureLogicCheck` 加 `TrustedClock` 用例（JVM 级）+ adb 改时间（设备级）

> **状态：✅ 已完成（设备级那半条待有真机时补做）**
>
> - `android/.../capability/TrustedClock.java`：`SystemClock.elapsedRealtime()` 为基准 + 每次心跳用 `serverTime` 锚定，偏差跳变超 60 秒 → `sync()` 返回 true。
> - **所有判定点都换成了 `TrustedClock.now()`**（13 个文件）：锁定判定 `LockEnforcer.buildInputs` × 9、放行截止（`anyGrantUntil` 比较 ×2、`setManualUnlockUntil` ×2、答题奖励 ×2）、`LockState.findNextLockAt` 的宽限、学习模式求值 ×4、敏感界面放行窗口 ×3、用量统计的「今天」、时间表边界闹钟。
> - **刻意不换的地方**（都写在 `android/README.md` §5.9 的取舍表里）：媒体文件名、日志行时间、中继节流窗口、`markServiceAlive` 的「最后活着」证据 —— 它们是**测量**不是**判定**，换过去只会让排查变难。
> - 两处顺手修掉的**真问题**：① `WatchdogScheduler.scheduleBoundary` 原来用 `RTC_WAKEUP` 排绝对时刻，孩子把时间调晚就等于让「22:00 锁屏」永不触发，改成「可信时钟算出还剩多久 → `ELAPSED_REALTIME_WAKEUP`」；② `ScreenCapturer.awaitImage` 的等待循环用墙钟判超时，改时间能让它一直等下去（截屏卡死），改用 `elapsedRealtime`。
> - `TrustedClock` 现在**不依赖 `EventLog`**：它只做时间数学，副作用（记 `tamper` 事件、补一次健康上报）交给 `AgentService.doHeartbeat` —— 这样它才能在普通 JVM 上被逐条钉死。
> - 家长端能看到的：动态里一条 `tamper` 事件 + 健康页的「孩子手机的时间和服务端相差 N 秒」（阈值同为 60 秒）。
> - **设备级验证没做**：`adb devices` 为空列表，`adb shell date` 改时间那条断言**一次都没跑过**，`android/README.md` §5.9 与 `docs/FEATURE-STATUS.md` §3B 都如实标注了。
> - 没有给「改时间」单独加一条站内通知：那需要通知支持结构化参数（标题里嵌分钟数），否则英文界面会出现「变量嵌在中文句子里」的句子；本轮按 §2.1 的事件清单执行，这一条记在这里备查。

## 3. P1 孩子端体验（让孩子愿意配合）

现在孩子端只有「被锁」和「设置页」，**没有任何正向出口**。孩子除了等家长，什么也做不了，
这是冲突的主要来源。

- **3.1 时间余额 + 申请**：孩子端显示今日剩余时间；「申请加时 / 申请延后锁屏 / 申请装某应用」
  → 家长端审批。审批范式直接复用 `AppAuditRequest` + `AppAuditPage`（已有）
>
> **状态：✅ 已完成（2026-10，第 2 轮）。** 孩子端锁屏页多了一个「申请使用时间」按钮，
> 选时长（15/30/60/120 分钟）+ 可选一句话理由；家长端新增 `/time-requests`（待审批 / 已处理
> 两个页签），批准时会**立即给孩子手机下发 `temp_unlock` 指令**，设备回报成功后
> `locked` 才真的变成 false —— 服务端绝不自己宣布「已解锁」。通知中心同步产出
> `child_request` 一条（带设备、可跳回本页）。
>
> **没有复用 `AppAuditRequest`**（原文的设想）：那张表的幂等键是 packageName、语义是
> 「能不能装这个包」、落地动作是装应用放行；加时申请的幂等键是 (设备, 类型)、落地动作是
> `temp_unlock`。硬塞一张表要靠一堆可空字段区分两种语义，家长端两个列表还会互相污染。
> 所以新建了 `TimeRequest` 表，复用它的**约定**而不是它的表：请假条式留痕、批准不删记录。
>
> 三条刻意的取舍：**① 家长只能改小不能改大**（孩子申请 120 分钟、家长给 30 是常态；
> 反过来只可能是误触或改包，服务端 `Math.min` 夹住，并把家长实际给的存进
> `grantedMinutes` 留痕）；**② 反复点「申请」收敛成一条**（按 设备+类型+pending 幂等，
> 内容没变时不刷新 `createdAt`，否则「已经等了多久」每点一次就重置，家长的待办也跟着乱跳）；
> **③ 已处理过的不能再改**（409「这条申请已经处理过了」—— 允许翻案的话，设备端那条
> 「已批准」的轮询结果就成了假的）。
>

## 7. 施工纪律（沿用本仓库既有规矩）

1. **契约先行**：先落字段名（像 `PLAN-agent-gaps.md` 那样出表），三端不各自发明
2. **新指令必须同时改** `COMMAND_TYPES`（`devices.constants.ts`）+ Android `CommandExecutor` 的
   `switch`，漏一处 = 静默不执行
3. **全量替换语义的上报接口空数组一律 422**：设备端查到 0 条应跳过上报，不要发空数组
4. **验证等级表**（§3A）：编译 / JVM / 设备级三列，没跑过的写「未验证」，**不许算成通过**
5. **不伪造**：做不到就如实降级并在界面写明，绝不返回假成功
6. **明确不做的仍然不做**：实时投屏/推流、真正的远程控制（注入触摸）、隐蔽录音
   （原因见 `PLAN-agent-gaps.md` §10 与 §3.9）
